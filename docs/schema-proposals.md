## 1. Widen `audit_logs_action_check` — **found in Phase 2, has a workaround**

**Blocks:** nothing. Working around it now.

`audit_logs.action` is constrained to six values:

```
CHECK (action = ANY (ARRAY['insert','update','delete','login','logout','login_failed']))
```

Part 6.5 asks for lockouts, password changes and password resets to be recorded
too, and none of those fits. I am mapping each event onto the nearest permitted
value and storing its real name in `new_values->>'event'` — see
`AUDIT_ACTION_FOR` in `modules/auth/auth.repository.ts`. So `account_locked` is
stored as `action = 'login_failed'` with `new_values->>'event' = 'account_locked'`.

Nothing is lost, but filtering by `action` is coarser than it should be: "show
me every password change" becomes a JSON predicate rather than an indexed
equality.

```sql
ALTER TABLE audit_logs DROP CONSTRAINT audit_logs_action_check;
ALTER TABLE audit_logs ADD CONSTRAINT audit_logs_action_check
  CHECK (action = ANY (ARRAY[
    'insert','update','delete',
    'login','logout','login_failed',
    'account_locked','account_unlocked',
    'password_changed','password_reset_requested','password_reset_completed',
    'refresh_token_reuse',
    'permission_denied'
  ]));
```

Safe: it only widens what is accepted, so no existing row can violate it.

**Recommendation:** approve. It is the difference between an audit log you can
query and one you have to grep.

## 2. Outbox table — **blocks Phase 5**

**Blocks:** the accounting event handlers, which Part 16 puts in Phase 5.

Module 10 requires the outbox pattern by name: the event is written in the same
transaction as the business change, and a worker delivers it. There is no table
for it. Without one, a fee payment either posts its voucher inside the payment
transaction (so an accounting failure rolls back a collected payment — wrong) or
after it (so a crash loses the voucher silently — also wrong).

```sql
CREATE TABLE event_outbox (
  id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  event_type     text        NOT NULL,
  -- What the event is about, so a handler can be idempotent: a voucher is
  -- posted at most once per (source_type, source_id).
  source_type    text        NOT NULL,
  source_id      bigint      NOT NULL,
  payload        jsonb       NOT NULL,
  status         text        NOT NULL DEFAULT 'pending',
  attempts       integer     NOT NULL DEFAULT 0,
  last_error     text,
  available_at   timestamptz NOT NULL DEFAULT now(),
  processed_at   timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT event_outbox_status_check
    CHECK (status = ANY (ARRAY['pending','processing','done','failed'])),
  -- One delivery per event per source. This is what makes replay safe.
  CONSTRAINT event_outbox_unique_source
    UNIQUE (event_type, source_type, source_id)
);

-- The worker's claim query: oldest available pending row first.
CREATE INDEX event_outbox_claim_idx ON event_outbox (available_at)
  WHERE status IN ('pending','processing');

-- The dead-letter view Part 5.9 asks for.
CREATE INDEX event_outbox_failed_idx ON event_outbox (created_at)
  WHERE status = 'failed';
```

The unique constraint is the important part: it makes the handler idempotent at
the database level rather than relying on the worker to remember.

**Recommendation:** approve before Phase 5. I cannot build the accounting
handlers correctly without it.

## 3. Inventory stock summary — **blocks part of Phase 6**

**Blocks:** the fast stock-on-hand read in Module 11. The module itself can be
built without it by summing `stock_movements` every time.

Part 9.4 calls for it explicitly and says to propose it.

```sql
CREATE TABLE item_stock (
  item_id       bigint PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,
  quantity      numeric(14,4) NOT NULL DEFAULT 0,
  -- Set inside the same transaction as the movement that changed it, so the
  -- reconciliation job can report drift against SUM(stock_movements).
  updated_at    timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT item_stock_non_negative CHECK (quantity >= 0)
);
```

**Recommendation:** approve, but it is not urgent — summing movements is correct
if slower, so Module 11 can ship first and gain this later.

## 4. Public identifier columns for receipts and certificates — **blocks one endpoint**

**Blocks:** the public verification endpoint in Part 12.

Part 12 wants a heavily rate-limited public endpoint that verifies a receipt or
certificate by number. Exposing `payments.receipt_no` directly is a problem:
those come from a sequence, so they are guessable, and anyone could enumerate
every receipt the school has issued.

```sql
ALTER TABLE payments
  ADD COLUMN public_ref uuid NOT NULL DEFAULT gen_random_uuid();
ALTER TABLE payments ADD CONSTRAINT payments_public_ref_key UNIQUE (public_ref);

ALTER TABLE student_leaving_records
  ADD COLUMN public_ref uuid NOT NULL DEFAULT gen_random_uuid();
ALTER TABLE student_leaving_records
  ADD CONSTRAINT student_leaving_records_public_ref_key UNIQUE (public_ref);
```

`pgcrypto` is already installed, so `gen_random_uuid()` is available. The printed
receipt or certificate carries the UUID; the endpoint returns only validity,
date and amount — never the student's name.

**Recommendation:** approve, or tell me to drop the public verification
endpoint. Building it on the sequence numbers would be worse than not having it.
